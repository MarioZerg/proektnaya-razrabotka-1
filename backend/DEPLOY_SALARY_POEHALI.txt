4. Убедись, что URL остался тем же.

**Что должно попасть в прод (обязательно проверить в коде перед деплоем):**

### A1. Пагинация админских начислений — по рабочим дням
- `GET` списка начислений: `?page=1` отдаёт до **2 календарных дней** `accrued_for` **целиком**.
- На странице — все начисления этих дней (все сотрудники), а не «первые 15 строк».
- `totalPages` = по числу уникальных дней, не по числу строк.
- Иначе фронт (день → роль → сотрудник) показывает дырявый день.

### A2. Бонус швей (акция 01.09–30.09.2026) закончился
- `?sewerBonus=1` после 01.10.2026 → `{ "active": false, "sewers": [] }`.
- Не возвращай `state: "finished"` со старым списком.

### A3. Номер заказа — заказ покупателя, не позиция/строка системы
В ответах `orderNumber` (и для `?my=1`, и для админского списка):
- OZON: из `ozon_posting_number` (или `order_number`) **без** суффикса `-0001`;
- WB: `wb_order_id` если есть;
- YM: `ym_order_id` если есть;
- иначе `order_number`.
В коде это SQL-хелпер `_ORDER_LABEL_SQL` в `backend/salary/index.py`.

**Не делать в salary:**
- Не возвращать пагинацию `LIMIT 15 OFFSET …` по строкам.
- Не менять формулы выплат/кассы/начислений — только A1–A3.

## Часть B — оптимизация появления модулей на «Финансах»

Проблема, которую уже ловили: на вкладке Финансы / Зарплата модули
(сводка, начисления, касса, тарифы, выплаты, у сотрудника — фильтр/календарь/список)
не появлялись нормально сразу — страница «собиралась» кусками с заметной задержкой,
приходилось отдельно просить оптимизацию. Сейчас во фронте снова много блоков
(папки ролей, касса по дням, календарь сотрудника) — нужно сразу в этом же запросе
сделать плавное и быстрое появление.

**Где править (фронт в этом же репозитории):**
- `src/pages/Finance.tsx` — загрузка данных админа/сотрудника
- `src/components/crm/finance/AdminFinanceView.tsx` — раскладка админа
- `src/components/crm/finance/MySalaryView.tsx` — экран сотрудника
- связанные карточки: касса, тарифы, выплаты, календарь (`MyWorkCalendar`), сводка

**Цели оптимизации (сделай по факту кода, не ломай API):**

1) **Не блокировать весь экран одним `loading`.**
   Каждый блок (начисления / касса / выплаты / тарифы / сводка / календарь)
   должен уметь показаться со своим скелетоном/спиннером, как только пришли ЕГО данные.
   Пока грузится касса — таблица начислений уже видна (и наоборот).

2) **Параллельные запросы, без водопада.**
   Админ: summary/operations, payouts, cashBox, employees — стартуют вместе,
   не «сначала employees, потом всё остальное по цепочке».
   Сотрудник: `fetchMySalary` для списка и отдельный запрос календаря за месяц
   не должны сериализоваться без нужды.

3) **Каркас страницы сразу.**
   Заголовки, фильтры, пустые карточки-оболочки рисуются сразу при входе на вкладку.
   Данные подставляются поверх — без скачка всей вёрстки, где можно сохранить высоту.

4) **Тяжёлые куски ниже первого экрана — не откладывать навечно, но и не душить первый paint.**
   Если есть смысл: `requestIdleCallback` / отложенный mount для тарифов или нижней
   кассы только после первого paint — ок. Но не так, что пользователь 2–3 секунды
   смотрит пустую страницу.

5) **Не ломать текущие фильтры и гонки запросов.**
   В `Finance.tsx` уже есть `operationsReqId` / `mySalaryReqId` — сохраняй отмену устаревших ответов.
   В календаре сотрудника — свой reqId на смену месяца (уже задумано).

6) **Не трогать** бизнес-логику зарплат, только UX загрузки/появления блоков.

**Ориентир «готово» для части B:**
- Админ открыл Финансы → за ~1 экранный кадр виден каркас; блоки догружаются независимо.
- Сотрудник открыл Моя зарплата → баланс/фильтр/календарь/список не ждут друг друга
  «все или ничего».
- Нет регрессии: пустые состояния и ошибки по-прежнему отличаются (баннер «Повторить»).
